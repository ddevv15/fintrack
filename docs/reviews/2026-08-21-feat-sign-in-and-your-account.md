## Summary

This ships spec 0004 end to end: the cents-to-minor-units rename, the currency/timezone profile columns with three defense-in-depth triggers, and the full InsForge Auth surface (sign up, verify, sign in, Google OAuth, password recovery, in-session password change, account deletion, and attempt limiting on all eight relevant actions, including the build-step-11 mail senders and code submitters). The implementation is careful and consistent: every database-level guarantee (currency lock, profile-completeness gate, timezone validity) has a matching app-level check that exists only to explain the refusal in words, never to be the real guard, and the migrations' `SECURITY DEFINER` comments are exactly as thorough as the spec demands. No blockers. Two majors: the shipped spec documentation (verify.md, the follow-up list, rationale.md) still claims the build-step-11 attempt limiting is unbuilt when the code in this same diff clearly implements it, and the new `lib/attempt-limit.ts` — the module carrying the fail-open security guarantee AC-8 rests on — has no test coverage at all. A few minor convention and documentation issues round it out.

## Major

### 🟠 Spec documents contradict the code they ship alongside, `docs/specs/0004-sign-in-and-your-account/verify.md:7`
**Problem**: `verify.md` (new in this diff) states "Build step 11, the rest of the attempt limiting, is specced and not yet built, so AC-8 does not fully hold" and marks five attempt-limiting checklist rows (lines 59–63) as "expected to fail until step 11". `docs/specs/0004-sign-in-and-your-account/index.md:120` still lists build step 11 as an open `[ ]` follow-up ("This is the one criterion this spec now states that the code does not meet"), and `rationale.md:115` repeats "build step 11 exists because the code does not yet meet it." But `actions/auth.ts` in this exact diff has `requestPasswordChange`, `resendVerification`, `verifyEmailCode`, `setNewPassword`, and `changePassword` all behind `refuseIfTooManyAttempts()` / `refuseIfTooManyAccountAttempts()` — step 11 is built. `docs/scope/scope.md` (also touched in this diff) correctly checks off "Finish the attempt limiting" as done, so the three spec files disagree with both the code and with scope.md.
**Why it matters**: These are exactly the documents `/check verify` and a future auditor read to decide whether AC-8 holds. As written, they either cause someone to skip re-testing paths that now work, or to believe a security-relevant gap (unlimited code guessing on password reset/verification/password change) still exists when it does not — the opposite failure directions of a review doc are both costly here.
**Suggested fix**: Update `verify.md`'s five "expected to fail until step 11" rows to reflect that step 11 shipped in this diff (check them off or re-verify and check them), and correct the `index.md` follow-up item and the `rationale.md` sentence to say the criterion is now met, consistent with `scope.md`.

### 🟠 The fail-open security guarantee in `lib/attempt-limit.ts` has zero test coverage
**Problem**: `lib/attempt-limit.ts` is new (214 lines) and carries the one behavior spec 0004 calls out repeatedly as load-bearing: attempt limiting fails open on any Arcjet error, throw, or missing key, and refuses on a genuine rate limit or bot decision with kind-specific wording. None of this is tested — not the fail-open branches (`catch`, `isErrored()`), not the deny branches (`isRateLimit()` vs the bot message), not the per-`AttemptKind` message selection. `grep -rln "attempt-limit\|refuseIfTooMany" tests/` finds nothing.
**Why it matters**: `TESTS = configured` for this project, and this is exactly the shape the review guide calls Major-when-untested: branching, error-handling, security-relevant logic. It is also the one place the whole feature explicitly says "get this wrong and the owner is locked out of their own money history" (fail-open) — the highest-consequence code in the diff to leave unverified. The `decide()` function already takes its Arcjet call as an injected callback (`ask: () => Promise<ArcjetDecision>`), which is precisely the shape that makes it mockable; it just is not exported.
**Suggested fix**: Export `decide` (or a thin wrapper) and add a unit test that stubs the `ask` callback to throw, to return an errored decision, and to return allow/deny/bot decisions, asserting the fail-open and message-selection behavior directly — the same spirit as the structural guard already used for `requestPasswordReset` in `tests/unit/auth-actions.test.ts`.

## Minor

### 🟡 Direct `process.env` read outside `lib/env.ts`, `actions/auth.ts:283`
**Problem**: `initiateGoogleOAuth` reads `process.env.NODE_ENV === "production"` directly to decide the `secure` flag on the code-verifier cookie. AGENTS.md rule 7 states environment variables are declared and validated in `lib/env.ts` with Zod, and code should "never read `process.env` directly." This is new in this diff (absent at the merge base).
**Why it matters**: It is a real, if low-risk, convention break — `NODE_ENV` is Next.js-managed so it is unlikely to be misconfigured, but the rule exists precisely so nobody has to reason case by case about which `process.env` reads are "the safe kind."
**Suggested fix**: Either add `NODE_ENV` to the `lib/env.ts` schema (Zod's `z.enum(["development", "production", "test"])` with a default) and read it from `env()`, or note this one exception explicitly in `lib/env.ts` the way `APP_CURRENCY`/`APP_TIMEZONE`'s demotion is documented there.

### 🟡 Currency-lock refusal is still recognized by matching raw trigger text, `actions/settings.ts:140`
**Problem**: `updateProfile` decides whether to show the friendly "your currency is fixed" message by testing `/currency cannot change/i` against `error.message`, i.e. the literal string raised by the `assert_currency_not_locked()` trigger in `migrations/20260819224157_currencies-and-profile-locale.sql`. The spec's own follow-up list (`index.md`) already flags this as unpinned and recommends keying off the error code instead. `tests/integration/locale-guards.test.ts:41` does assert the trigger raises text matching the same regex, which will catch a drift in one direction, but the two independently-editable strings (trigger message, action's regex) still have to be kept in sync by convention rather than by a shared constant or error code.
**Why it matters**: If someone rewords the trigger's exception message without updating this regex (or without noticing the integration test also needs the real backend to catch it), AC-12's "plain words" refusal degrades silently into a generic "Could not save that" error.
**Suggested fix**: As the spec follow-up already suggests, key off `error.code` (Postgres `check_violation`, `ERRCODE = 'check_violation'` is already set on the trigger) plus a shared constant for the message substring, rather than a bare regex literal duplicated between the action and the migration.

### 🟡 Stale docstring contradicts the shipped design, `components/auth/SetupForm.tsx:16-21`
**Problem**: The comment says "Google sends neither value, and where a password sign up never lands, because its form collected both." But per `migrations/20260820095627_new-user-writes-name-only.sql` and the `AppLayout` completeness redirect (`app/(app)/layout.tsx`), a password sign up's form only ever collected email/password/name — currency and timezone are null for every new account, password or Google alike, and every account lands on `/setup`. This matches `rationale.md`'s "Ratified at build time" item 1 and the migration's own comment ("collected once on /setup by every new account, whether it signed up with a password or with Google"), so the SetupForm docstring is a leftover from an earlier design iteration.
**Why it matters**: A comment that explains *why* incorrectly is worse than no comment — a future maintainer reading `SetupForm.tsx` in isolation would believe password accounts skip this screen, which is false.
**Suggested fix**: Update the docstring to say every new account, password or Google, lands here once, matching the migration comment's wording.

## Strengths

- Every app-level guard (currency lock, profile completeness, timezone validity, `delete_own_account`'s parameterless design) is backed by a real database constraint or trigger that is the actual enforcement; the app-level check exists solely to produce a readable message. This is applied with real discipline across `actions/settings.ts`, `actions/auth.ts`, and all three new migrations.
- `Settings`'s discriminated union (`lib/settings.ts`) makes "profile not yet complete" structurally impossible to read as "use a default" — a caller cannot reach `currency`/`timezone` without narrowing on `isComplete` first.
- `lib/time.ts`'s `RENAMED_ZONES` table, closing the gap between ICU's legacy timezone names and Postgres's `pg_timezone_names`, is a genuinely subtle correctness fix (someone in Delhi could otherwise never get off `/setup`) with a clear comment explaining why it exists and a drift test backing it.
- The `after()`-deferred password-reset email send, with a structural guard test (`tests/unit/auth-actions.test.ts`) proving the send stays deferred rather than re-introducing a timing side channel, is a well-reasoned trade given the runner is scoped to pure logic.
- Integration coverage (`locale-guards.test.ts`, `schema-drift.test.ts`) exercises the currency lock, timezone trigger, completeness trigger, and cross-account isolation against the real backend, not mocks — exactly the surface where RLS and trigger bugs actually hide.

## Test coverage

Unit tests cover `formatAmount`/`currencySymbol` across zero/two/three-decimal currencies, `today()`/`monthRange()`/timezone renaming, the `env()` schema (including the `UI_GALLERY=`/`ARCJET_KEY=` empty-string regressions), and schema parsing. Integration tests cover the currency lock, timezone trigger, profile-completeness trigger, cross-account isolation on `profiles`, `currencies` read-only RLS, and `delete_own_account()`'s parameterless safety, all against a real backend. E2E covers route protection, corrupted-cookie handling, and WCAG 2.2 AA on all five public auth screens in both themes. The one real gap is `lib/attempt-limit.ts` (Major, above) — the fail-open/deny branching that AC-8 is built around has no test anywhere in the suite.
